# RTL 接入设计与阶段边界

2026-11-24。遵循[项目使命](../../PROJECT_MISSION.md)、[工程框架](../../ENGINEERING_FRAMEWORK.md)及[模型规则](../../docs/development/model_rules.md)。**当前交付为文档与接口设计，所有RTL行为和验证流程均尚未实现。**

## 1 研究什么

RTL接入应帮助回答：选定数字机制在有限位宽、端口、缓冲和周期条件下是否保持任务语义；架构模型对延迟、II和资源瓶颈的解释在什么条件下成立；具体结构能够为面积、时序或成本提供什么证据。

| 问题 | 最小设计对象 | 所需证据 |
| --- | --- | --- |
| 累加位宽或归约组织是否影响正确性 | 一个整数MAC/点积及明确数值契约 | 独立整数参考、逐步溢出和边界向量 |
| 有限缓冲是否限制供数 | 一个FIFO或局部存储/计算连接 | 接纳/取走、占用、背压与守恒轨迹 |
| 分析L/II是否适用于实际组织 | 一个明确item含义的流水线 | 同初态/同输入的无阻塞和阻塞周期对照 |
| 某个结构的物理代价如何 | 具名实现和完整约束/工艺库 | 综合/时序/活动数据及适用域；未知项显式保留 |

这些对象可独立验证；不依赖完整芯片、节点、LLM或平台事件引擎。通用接口从实际单元需求中提炼，最终也可用于计算、存储或互连课题。

## 2 怎样建模与划分所有权

| 位置 | 责任与边界 |
| --- | --- |
| `rtl/` | 未来数字实现及其私有寄存器/队列、端口、时钟和复位语义；当前只有文档 |
| `chipmodel` | 功能/分析模型和硬件资源身份；保留独立Python调用，不导入或启动HDL工具 |
| `workloads`、`compiler` | 任务语义、独立数值参考及映射；任务到RTL接口的适配需保留原始输入身份 |
| `evaluation` | 未来显式装配参考、驱动、工具调用与比较；拥有实验状态，不拥有被测硬件队列 |
| `simulator` | 按需接入外部时间/事件适配；一次实验只由选定时间执行方推进该资源 |
| `costmodel` | 消费有版本/条件的特征化结果；不将综合单元数自动换成面积/功耗 |
| `configuration`、`contracts`、`artifacts` | 复用参数解释、标准库交换对象和产物保存；本轮不新增可执行schema、适配器或import依赖 |

数据关系记录数值格式、布局、实际字节和数据版本；控制关系记录接纳、呈现、取走、错误与取消；时钟关系记录采样边沿、复位和域；物理关系记录resource_id、owner、实际存储/端口/实例和约束来源。

同一实验中某资源只能由一个选定后端更新运行状态。Python参考和RTL可以在隔离副本上对照；不能让二者同时拥有同一动态队列或重复计入同一MAC/存储服务。RTL层级名通过显式映射绑定已有resource_id，文件/目录名不代表新的物理资源。

当前仍保留[13模块依赖清单](../../docs/architecture/modules.json)及原Python打包范围。`rtl/`作为文档入口单独导航；后续若加入需要管理的生产代码，再按实际职责评审模块登记和工具边界，不能靠新增目录默认授予反向依赖。

## 3 接口选择与模型精度

[接口规范](interfaces.md)给出可选基础草案`rtl-stream/v0-draft`：单时钟、同步高有效复位、按序的一入一出请求/响应、有限在途容量。具体Unit须明确采用此profile或列出完整差异；未填写的位宽、payload、延迟和容量不自动获得默认值。这不声称兼容AXI、PCIe或某厂商指令。

可综合数字部分与测试专用行为模型分开标记。CIM数字控制、编码及有限位宽处理可作为未来数字实现；电导阵列、ADC/DAC/TIA等电气行为须注明使用的外部/行为模型和适用条件。使用理想ADC码作为输入只能验证该数字输入域内的逻辑，不能据此证明模拟前端可实现。

未来优先考虑可综合SystemVerilog子集；如果采用Verilog或特定工具限制，在Unit规格中记录语言、版本及不支持的构造。本轮不固定某台电脑的工具路径，也不把版本命令可执行作为仿真通过证据。

文档准备的验收是：含义一致、引用可达、适用域清楚、设计与证据分开，以及既有代码和工作流设置保持原状。它不提升任何RTL功能、周期精度或物理可行性的实现状态。
