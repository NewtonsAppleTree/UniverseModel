# 第一性原理：真正需要守住的东西

## 1 整体目标

芯片架构的价值是以可接受的质量和成本完成真实工作。计算峰值、容量、带宽、层数和设备数都是手段。项目的核心产出不是更大的模型，而是能够解释“为什么这个组织方式在这些条件下更好”的证据。

最简因果链为：工作语义决定计算与数据需求；数据位置和映射决定路径；依赖与有限资源决定时间；状态变化和物理实现决定能量/面积/热；输入和模型不确定性限定结论范围。

## 2 六条不可跳过的原则

1. 语义优先。错误结果、不可接受的数值质量或缺失的操作不能通过更高吞吐补偿。
2. 数据移动有代价。读取、复制、格式转换、规约和同步必须发生在真实位置与路径上；存算融合改变路径，不消除全部代价。
3. 资源有限。端口、buffer、发射槽、ADC、链路和散热能力决定并发边界，峰值相加不能证明系统可达到。
4. 因果不可违背。结果不能在数据到达前可见，后继不能越过依赖，调度器不能利用未来信息。
5. 物理成本有条件。精度、工艺、电压、温度、布局和负载改变成本；模型层次与校准数据限定可信范围。
6. 结论必须可追溯。一次收益需要输入、参数、映射、成本、代码与统计口径共同支撑，不能只留下图表。

## 3 每个模块的最核心问题

| 模块 | 第一性问题 | 最需要守住的量/不变量 |
| --- | --- | --- |
| contracts | 双方是否在说同一件事 | 身份、单位、语义、完成条件、版本 |
| configuration | 此次实验到底用了什么 | 唯一有效配置、依赖、来源与可实现性 |
| costmodel | 这个动作在此条件下付出什么 | 覆盖边界、量纲、适用域和误差 |
| chipmodel | 有限芯片资源怎样完成计算和移动 | 容量、端口、状态、数据局部性和数值规则 |
| systemmodel | 设备怎样持续获得数据 | 地址/路径、共享 I/O、主机与注入能力 |
| clustermodel | 工作扩展时必须穿过什么瓶颈 | 割集、共享链路、路由和端点能力 |
| workloads | 真正需要完成什么 | 代表性输入、语义、质量和独立参考 |
| compiler | 怎样保持语义并降低资源需求 | 依赖、生命周期、映射合法性和实际流量 |
| runtime | 何时能够合法提交下一步 | 可观测状态、背压、顺序和软件成本 |
| simulator | 这些行为以怎样的时间顺序发生 | 因果、守恒、确定性和正确终止 |
| artifacts | 结果是否仍能解释和重现 | 完整来源、不可变身份和提交状态 |
| evaluation | 比较是否回答原问题 | 公平约束、端到端指标、失败与不确定性 |
| ui | 用户是否知道自己改了什么 | 同一参数真相、依赖解释与结果来源 |

config、data、tests、example、docs、tools 是这些职责的载体。它们分别服务配置、证据、验证、可重现示范、知识维护和开发效率，不应再产生平行业务状态。

## 4 对不同硬件的核心关注

CPU/GPU/NPU：先看支持语义、可利用并行度和数据供给，再看峰值资源。并行单元无法替代必要串行段；执行宽度增加后，寄存器、缓存和互连需求也增加。

CIM：核心是计算与权重驻留的结合是否减少系统中的主要移动，以及编码、转换、累加、编程和误差补偿是否吞掉收益。cell 数是物理载体，有效运算能力取决于可同时激活与读出的范围。

3D CIM：核心是空间距离、可用连接和散热路径共同改变。层数增多不创造无限垂直带宽，投影面积缩小不意味着硅面积或热阻下降。

HBF：核心是新存储层的访问能力是否匹配目标对象的局部性与更新需求。容量、吞吐、访问粒度、延迟和寿命是不同约束，不能由单一“高带宽”名称推断。

双 Die 与异构：核心是分区后的局部收益能否覆盖边界成本。拆分引入通信和同步，也可能改善容量与制造；必须看数据怎样跨过边界。

集群：核心是局部工作可并行的比例和全局数据交换的必要性。更多卡只增加部分能力，网络割集、同步和负载不均衡可能更快成为主导。

## 5 判断模型是否值得继续细化

若新增细节不会改变可行性、排序或关键误差，则优先保留简洁模型。若结论取决于未建模的热降频、ADC 共享、页访问或网络热点，则该细节必须显式进入模型或变成结论限制。

应优先回答四件事：结果是否正确；主要时间/能量花在哪里；改变哪个可实现决策能改善它；结论对哪个未知量最敏感。可以把每一项模型扩展与其中一个问题绑定，避免堆积没有决策价值的细节。

## 6 每次架构评审的必要证据

用同一张因果链检查：工作量/质量 → 放置与数据路径 → 容量/资源界 → 实际时序/争用 → 能量/物理约束 → 误差与复现。若链条中某处只有一个未经解释的利用率或效率常数，应追问它覆盖哪些机制、来自哪里、在哪些条件下有效。

最终设计结论应可以表达为：“在负载 W、质量 Q、预算 C 与参数范围 U 下，方案 A 通过减少路径 D/缓解资源 R 改善指标 Y；代价是 Z；证据来自这些可复现实验。”不能支持这种表达时，先补证据再扩大模型。

## 7 抽象不能丢掉决定结论的信息

模块越多不代表覆盖越完整，细节越多也不代表模型越可信。一次抽象必须保留会影响当前决策的状态、资源竞争和数据可见性，并把被省略的机制与适用条件说明白。

需要进一步守住的是三种区分：完成与可见性的区别、已知成本与未知覆盖的区别、执行成功与结论有效的区别。[补充审视](design_review.md)把它们落实为优先级、模块责任和可手算的边界案例。
