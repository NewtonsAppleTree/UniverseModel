# 指令设计与仿真精度选择

本提案说明什么时候需要硬件指令，什么时候使用代码、周期或 RTL 模型，以及怎样让它们进入同一个局部仿真接口。优先研究 CIM array + DAC/ADC + 缓冲，其他组件按[组件目录](../reference/hardware_component_catalog.md)扩展。当前实现情况见 [STATUS](../STATUS.md)。

## 1 仿真精度由问题决定

| 问题 | 适合的起点 | 还不能证明什么 |
| --- | --- | --- |
| 数值、位切片、累加和饱和是否正确 | Python/C++ 功能模型、独立参考 | 周期、吞吐或能耗准确 |
| ADC 数/阵列规模/缓冲容量如何影响资源界 | 条件解析成本、工作量与容量模型 | 真实并发和排队已被还原 |
| ADC 共享、DMA 与计算能否重叠 | 有限资源离散事件模型 | 每个 RTL 信号都按周期一致 |
| 发射、bank、pipeline hazard、credit 怎样逐拍变化 | 代码级周期模型或 SystemC 时序模型 | 已满足物理时序、PPA 或综合规则 |
| 指令解码、寄存器更新、ready/valid、复位是否正确 | RTL 仿真及断言，必要时形式验证 | 布局布线后的最大频率与功耗 |
| ADC 精度、DAC 稳定、阵列寄生和读噪声是否合理 | 电路/混合信号仿真、器件数据或实测校准 | 自动覆盖完整系统负载与争用 |
| 目标频率、面积、时序裕量和动态功耗是否达标 | 综合、STA、物理实现与相应活动/工艺数据 | 所有运行情景或产品可靠性均满足 |

代码级仿真也能逐周期建模。RTL 的价值是验证具体数字逻辑实现；不能因为使用 RTL 就把未建模的 SRAM 宏、ADC 或模拟阵列视为已验证。SystemC 本身不保证某种精度，仍需声明模型和时间语义。

推荐首批使用 Python 装配、数值验证与事件模型。计算和事件规模达到明确瓶颈后再用 C++/Rust 等优化热点；公共协议不绑定语言。无需在第一次局部 CIM 实验前建立整芯片 RTL。

语言分工、跨语言粒度及带类型的 Unit 参数/状态组织，见[Unit 类与参数设计](../../chipmodel/docs/unit_model_design.md)。宿主执行更快不代表目标周期更少，两种时间单独记录。

## 2 首批 CIM 模型怎样逐步细化

第一层是可验证的数值链：输入编码 → 差分/位切片权重映射 → 阵列求和 → 量化 → 移位累加。先用理想且范围明确的模型验证整数意义和输入输出；随后分别加入饱和、器件失配、编程误差、读噪声与漂移。

第二层是资源事件：DAC 通道、阵列求值、采样保持槽、ADC 组、数字累加和缓冲有各自延迟、II、容量和占用。必须决定 ADC 转换时阵列是否能开始下一次输入，以及上一组样本是否仍有效。

第三层只细化影响结论的部分。例如 ADC 共享策略影响排队，就细化 MUX 与 sample/hold；硬件发射影响流水，就细化控制器周期；阵列非线性改变精度，就引用电路或实测响应表。

模拟/混合信号宏可以在 RTL 中使用行为模型做数字控制联调；此时验证的是接口、顺序和模型所声明的行为，模拟电路精度仍由其独立校准依据支撑。

## 3 时钟周期与操作周期数

固定时钟下，时钟周期 Tclk=1/f，N cycles 对应 N/f 秒。一次操作的延迟、发射间隔与占用可以不同。多时钟域使用统一时间轴，各域周期数单独报告。

物理上可行的时钟周期取决于组合关键路径、寄存器 setup、时钟偏差和时序裕量等约束；代码模型中填入 1 GHz 并不证明电路可以达到它。RTL 功能仿真也不能替代 STA。

ADC 的转换时间、阵列稳定时间可能以秒给出，不一定是整数数字控制周期。模型需说明在什么边界量化，取整是否保守，跨域同步是否另计。不能将多个域的 cycles 无条件求和。

## 4 四层操作表示

| 层次 | 例子 | 主要所有者 |
| --- | --- | --- |
| 工作语义 | MatVec、GEMM、量化、规约 | contracts/workload、workloads |
| 映射与执行计划 | 哪个 tile、哪个 buffer、哪些依赖和传输 | compiler；也可由手工或导入工具按公共契约生成 |
| 目标指令或硬件描述符 | 宏启动、DMA copy、barrier、weight program | ISA/描述符契约；compiler lowering 或手工汇编消费 |
| 微操作与内部阶段 | DAC bit phase、MUX select、ADC group、累加写回 | chipmodel 控制与组件；必要时 RTL 实现 |

公共计划不必一开始具有二进制指令编码。组件台架也可以直接请求一次 array evaluation 或 ADC conversion。是否暴露某个微操作取决于硬件可编程性与研究范围，不能把模型内部每个阶段强制设计成 ISA 指令。

对于 CPU/GPU，采用明确的既有 ISA 或任务摘要，不能用自创的通用 opcode 声称准确模拟某厂商指令。对于自定义 CIM/NPU 加速器，可以设计满足控制需求的设备 ISA 或命令描述符。

## 5 CIM 首版可选的设备操作集

建议先用人可编辑的助记符和字段描述操作，验证语义后才决定指令位宽与编码。表中操作是候选集，不要求一开始全部实现，也不为 TSU 假定专有 ISA。

| 操作类 | 关键操作数 | 完成语义与注意事项 |
| --- | --- | --- |
| WEIGHT_PROGRAM | 目标阵列、权重引用、编码/校准版本 | 编程/校验完成后生成有效权重世代；计算期间是否允许改写须声明 |
| COPY / TENSOR_COPY | 源/目的、长度或 shape/stride、路径、completion token | 分开接受、源释放、目标可见；张量搬运按能力扩展 |
| CIM_MVM | 阵列组、输入/输出、映射、数值模式、weight_epoch | 完整目标精度输出可见；内部可展开 DAC/ADC/累加 |
| REDUCE / CONVERT | 部分和、格式、缩放、舍入、目标 | 数值和位宽严格定义；不能默认免费后处理 |
| WAIT / SIGNAL | token、世代、参与范围 | token 标识事件，不替代数据可见性规则 |
| BARRIER / FENCE | 参与者、内存/设备范围、访问类别 | 区分控制同步与内存顺序，不能默认为全局同步 |
| CALIBRATE | 范围、算法/参数、目标校准版本 | 明确占用、数据变化与失效的权重/成本依据 |
| CONFIG / RESET | 被允许修改的域、边界条件、epoch | 不允许任意修改进行中的资源；复位处理残留事件 |

如果硬件仅提供宏级 CIM_MVM，DAC/ADC 阶段由控制器生成微操作。如果研究可编程外围，再定义专用指令子集。两个模式可共享组件，却必须明确哪个层级拥有时序和仲裁。

## 6 冻结编码之前先冻结什么

每条指令先定义输入/输出、副作用、前置状态、非法行为和异步生命周期，再谈 opcode 长度。至少回答：

1. 精度、布局、累加位宽、符号、舍入、饱和及异常是否明确？
2. 地址空间、对齐、stride、掩码、越界和别名如何处理？
3. 提交/发射/退休/输出可见分别意味着什么？哪些操作可重排？
4. token/queue ID 位宽与复用世代怎样避免 ABA 和过期完成？
5. 依赖、RAW/WAR/WAW、fence 与原子操作的范围是什么？
6. 部分完成、取消、设备复位和错误传播怎样影响目标存储？
7. 权重重新编程、校准或数值模式变化是否使已有计划失效？
8. 不支持的可选扩展如何发现与拒绝？

随后选择固定或变长指令、描述符间接寻址、立即数、寄存器/队列标识、端序、编码版本和保留位。大型 tensor 描述通常适合引用描述符，而非把完整 shape/stride 塞进每条指令。

设备 ISA 可以约束顺序和最低同步条件；普通功能语义不要写死在所有实现上都相同的完成周期。时序由实现、结构、资源竞争和工作条件决定。若某硬件接口有严格周期要求，应作为该目标配置的明确契约。

## 7 指令相关内容放在哪里

| 内容 | 建议归属 |
| --- | --- |
| 公共操作、数值与内存语义 | contracts/workload、plan、events；成体系后可新增 contracts/isa |
| 可编辑的目标操作定义与编码描述 | 版本化 ISA 资源；configuration 管可选特性和合法参数 |
| 目标能力、寄存器/队列/控制状态 | chipmodel/control 及具体 CPU/GPU/NPU/CIM 模型 |
| lowering、汇编/反汇编、目标选择 | compiler/src/lowering；确有需要再新增 targets 子目录 |
| 手写指令与设备台架 | example 中的局部用例；经同样的契约检查 |
| 指令/描述符驱动适配 | simulator/adapters |
| 软件提交、stream、动态调度 | runtime |
| 数值与语义独立参考 | workloads/reference；独立于目标 lowering 的实现 |

指令表可以作为生成文档、编码器与测试输入的共同来源，但不要让唯一参考与被测实现共用全部逻辑，否则同一个错误可能在两边同时出现。需要独立语义参考和外部已知例。

## 8 RTL 与外部模型如何接入

使用适配器把公共请求翻译成 RTL 引脚、总线事务或指令描述符，把握手、完成、错误和输出翻译回来。组件能力说明背压、时钟、复位和支持的操作子集。

一个局部例子是：Python 激励 → RTL 控制器/缓冲握手 → 行为级 CIM 宏 → RTL 结果队列。这样可以验证数字控制，不需要整芯片 RTL。另一个例子是事件级系统调用经过校准的 RTL 服务摘要，不在每个系统请求上启动 RTL。

联仿需要额外定义：统一时间与时钟比例、事件同步点、数据序列化、输入稳定和输出采样相位、跨域延迟、复位、随机性、超时与错误传递。只有证明两次同步之间不会出现影响对端的更早事件，才可批量推进；否则采用逐周期或保守同步。

simulator 管全局时间；RTL 适配器推进局部时钟并报告外部可见事件。不能让事件模型和 RTL 各自独立推进同一资源并重复计时。snapshot 只有在全部参与模型能恢复时才可承诺 Resume。

Verilator/cocotb 可作为数字 RTL 工具候选，SystemC/TLM 可作为事务联仿候选；具体选择需按接口、语言、性能和可用工具验证。Flash/DRAM/NoC 外部模型也采用同类适配原则。本文不声明已完成这些工具集成。

## 9 验证阶梯与进入条件

| 阶梯 | 验证内容 | 何时进一步细化 |
| --- | --- | --- |
| 语义 | 位切片、符号、量化、累加、可见性与错误 | 数值结果或副作用尚不一致 |
| 资源 | ADC 分组、buffer 租约、bank 冲突、重叠、排空 | 结论受流水线或仲裁细节影响 |
| 周期 | 逐拍发射、握手、hazard、CDC 与复位边界 | 需要验证具体数字控制实现 |
| RTL | 指令/协议一致、时序序列、断言与随机压力 | 需要面积/频率/功耗或电路证据 |
| 外部校准 | PVT、输入规模、访问模式、并发与误差 | 偏差或外推足以改变设计选择 |

比较两种精度必须固定输入、初态、测量与成本边界。没有校准的模型仍可用于条件比较，但应给出敏感性和适用范围；不会因为升级实现语言或生成更多事件而自动更准确。

## 10 首批建议

先实现一条小规模、参数可编辑的 CIM 数值与事件路径，允许手写请求直接运行；包括输入缓冲、DAC、差分阵列、采样保持、共享 ADC、移位累加、输出缓冲和最小控制器。权重默认显式预加载，同时记录编程成本未覆盖；随后加入 WEIGHT_PROGRAM 和冷启动实验。

第一批比较 ADC 共享数、输入位串行方式、缓冲槽数和接收端压力；第二批加入条件误差与真实外围成本。只有当控制流水、接口协议或特定电路误差影响结论时，再挑选相应局部做周期、RTL 或电路验证。数字 GEMM 可以作可选功能/成本对照，不作为启动 CIM 研究的先决条件。
