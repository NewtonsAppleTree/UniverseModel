# 异构芯片封装与集群建模规划

UniverseModel 扩展为能够组合 CPU、GPU、NPU、CIM 和 3D CIM 的多层架构建模平台。芯片内多核、封装内多裸片、节点内多卡和集群内多机分别表达，通过统一资源、端口、数据引用和时间语义连接。当前工作仍以架构定义、功能模型、映射和性能评估为主，RTL 用于后续关键模块校准。

本规划中的 HBF 指 High Bandwidth Flash；duo die 按双裸片 Dual-Die 处理。相关模块目录与设计文档现已建立，执行接口和模型仍待实现。当前模块边界以 docs/architecture/design.md 和 modules.json 为准。

## 1 模块边界与设计判断

工程已增加 systemmodel 和 clustermodel 的结构，将 chipmodel 的组合范围明确到封装。多核放在 chipmodel 内；板卡、节点和集群按各自管理的资源与共享瓶颈建模。这样可以在单芯片模型成熟后复用它，也可以用粗粒度设备模型先开展系统实验。

| 模块 | 建模范围 | 核心职责 |
| --- | --- | --- |
| chipmodel | Core、Tile、Die、Package | 计算、存储、片内及跨裸片通信、封装集成 |
| systemmodel | Board / Card、Node | CPU 插槽、设备实例、主存、NUMA、PCIe / CXL、NIC |
| clustermodel | 多 Node、Fabric、Switch、Rack / Pod | 网络拓扑、共享链路、路由、拥塞、资源分组 |
| compiler | 单设备和跨设备映射 | 切块、分区、放置、数据布局、静态依赖 |
| runtime | 软件执行策略 | 派发、流与队列、通信算法、动态策略 |
| simulator | 所有建模层次的执行 | 时间推进、事件、资源争用、统计与终止 |
| configuration / contracts | 公共配置与契约 | 参数定义、解析校验、版本、资源与数据语义 |

runtime 表达被建模的软件行为，simulator 表达运行这些行为的仿真机制。AllReduce 的分块与通信步骤属于软件通信层；交换机只处理其收到的流量。具备硬件归约能力的交换机应显式声明对应操作，不能默认具有该能力。

clustermodel 负责硬件资源与连接。作业放置、模型并行策略和动态负载均衡分别由编译映射或运行时策略处理。首版只调度一个实验内的工作负载，生产集群管理、容器平台和多租户服务留待出现明确需求时引入。

## 2 同时保留物理结构与逻辑资源视图

### 2.1 物理包含关系

典型层次为 Cluster → Node → Board / Card → Package → Die → Tile / Core → Engine / Array。Rack、Pod、Socket 作为需要时启用的中间层；板卡也可以省略，例如加速器直接安装在主板上。GPU 的 SM / CU、NPU Tile、CPU Core 和 CIM Macro 各有独立资源含义，不使用一个通用 core_count 换算算力。

| 对象 | 物理含义 | 建模约束 |
| --- | --- | --- |
| Package 封装 | 一个或多个计算、I/O 或存储裸片的集成边界 | 标明电源、散热、外部接口与面积边界 |
| Die 裸片 | 具体工艺上的一片芯片 | 可以含多种计算单元和多个时钟域 |
| Card / Board 板卡 | 一组封装、板级连接、电源和存储 | 不要求一张卡仅有一个设备 |
| Node 节点 | 可管理的主机或计算节点 | 定义 CPU、主存、设备与 NIC 的连接 |
| Cluster 集群 | 多节点及连接它们的网络资源 | 不假设节点同构或网络全互连 |

同一物理实例仅有一个所有者，以稳定 ID 被其他视图引用。资源数量沿包含关系汇总；逻辑分组不再拥有一份实体，防止在卡、设备、裸片之间重复统计。总硅面积按实际裸片累计，封装占地由位置、堆叠与封装边界确定；3D 堆叠后的占地不能直接用各裸片面积之和代替。

### 2.2 软件可见设备与执行资源

DeviceView 表示软件看到的 CPU、GPU、NPU 或 CIM 设备，指向其实际资源。一个设备可跨多个裸片，一个裸片也可提供多个逻辑设备或分区。双裸片 GPU 不自动等于两个 GPU Rank。是否共享地址空间、缓存一致性或统一内存，需要各自声明。

CPU、GPU、NPU、CIM 均作为可选择和组合的资源族。实现上另外记录 engine_kind 和 compute_mechanism：NPU 内部可以同时含数字 MAC 和 CIM Engine，CIM 也可以独立暴露为设备。CIM 不应被限制为所有 NPU 之外的互斥类别。

| 执行资源 | 需要表达的能力与结构 | 首版可采用的抽象 |
| --- | --- | --- |
| CPU | ISA、核数、SIMD、缓存、NUMA、控制与主机开销 | 算子或任务服务模型；需要时细化微架构 |
| GPU | SM / CU、SIMT、矩阵单元、寄存器与共享存储、访存 | 经校准的算子模型或 Tile 级资源模型 |
| NPU | 张量操作、数据流、片上存储、DMA、数值格式 | 阵列、存储、搬运与队列模型 |
| CIM | 介质、计算域、编码、阵列、外围、装载及误差 | 完整宏操作与资源占用模型 |
| 3D CIM | CIM 能力加阵列层次、跨层访问、外围共享与热约束 | 分层宏或裸片组合模型 |

不同设备之间只允许映射受支持的操作与精度。性能库必须按形状、布局、精度、批量和适用条件查询；一个 TOPS 数值不足以代表 CPU、GPU、NPU 或 CIM 的执行行为。

一个用于检查组合能力的例子是：2 个节点，每节点含控制 CPU、1 个 GPU 设备、1 个 NPU 设备和 1 个 CIM 设备。其中 CIM 设备对应双计算裸片封装，两个裸片形成 3D 堆叠，并连接 HBM 与 HBF。这个例子描述研究配置，不代表已校准的产品。

若每个 CIM 裸片内部再采用多层阵列，阵列层数作为裸片内部参数。该配置有 2 个逻辑 CIM 设备、4 个 CIM 计算裸片；加入的存储及 I/O 裸片另计。它同时包含设备异构、三维 CIM、封装组合和多机通信。

### 2.3 五类关系分别保存

- 包含关系：谁实际拥有哪个资源，用于结构、生命周期和面积统计。
- 通信关系：哪些端口相连、走哪条路径、共享哪些链路和队列。
- 地址与一致性关系：内存在哪里、谁能访问、何时可见、是否缓存一致。
- 执行关系：任务、Rank、模型分区与物理资源怎样绑定。
- 物理耦合关系：位置、电源域、热邻接和共享功率预算。

包含结构是树或森林，通信与热耦合通常是图。不能用父子层次推断所有节点互通，也不能因存在链路就假设具备跨设备 Load / Store、缓存一致性或原子操作。

## 3 双裸片与三维集成

### 3.1 数量与集成方式分别配置

Dual-Die 表示双裸片组织，不指定 2D、2.5D 或 3D 集成方式。应分别记录 compute_die_count、memory_die_count、io_die_count 和总实例数。所谓“双计算裸片”封装还可能包含 I/O 裸片、HBM 和基底逻辑，不能把总 die_count 固定为 2。

| 集成方式 | 关键结构 | 关键参数 |
| --- | --- | --- |
| 单裸片 Monolithic Die | 片内多核、片上网络 | 工艺、面积、片内连线和资源组织 |
| 2D 多裸片封装 | 裸片并置、封装基板连接 | 接口数量、距离、链路与引脚预算 |
| 2.5D | Interposer 中介层或局部桥接 | 裸片位置、桥接连接、接口密度与带宽 |
| 3D 多裸片堆叠 | TSV、Micro-bump 或 Hybrid Bonding | 堆叠顺序、垂直接口、节距、热路径 |
| 单裸片内三维结构 | 多层器件或三维存储阵列 | 内部阵列层数、寻址、选择和共享外围 |

封装可同时包含 2.5D 连接和局部 3D 堆叠。不要用一个全局 packaging=3d 覆盖全部连接；每组堆叠和每条连接分别声明实现方式。

Apple M2 Ultra 是两片 M2 Max 裸片通过封装互连组成产品的公开例子 [2]；AMD MI300A 展示 CPU 与 GPU 的组合 [1]。这些例子用于确定对象边界，不用于直接给未知设计赋予吞吐或能效。

### 3.2 3D CIM 的三种建模情形

**单裸片内的三维 CIM 阵列。** 例如利用三维存储器件执行阵列内运算。array_layers 属于器件和阵列模型，不能增加封装裸片数量。需要记录层选择、字线与位线、可并行访问层数、编码、感测和层间结果合并。公开的 3D FeNAND A-CiM 研究说明单元、非单元电路及页面组织需要共同优化 [7]。

**多个 CIM 裸片堆叠。** 多个 CIM Die 与逻辑基底或外围裸片组合。die_stack_depth、垂直端口、跨层流量、共享 ADC / 累加器及功率预算属于实际结构。增加层数可能增加权重容量，也可能受共享外围和出栈带宽限制。

**CIM 与数字逻辑异构堆叠。** CIM 裸片与 NPU、向量、控制或存储裸片共同集成。需要明确输入、权重、部分和及输出分别在哪一层，以及哪条路径完成转换和归约。单纯在数字逻辑上堆存储，并不会自动成为 CIM；必须具有明确的阵列内或紧耦合外围计算操作。

三种情形可以组合。应同时保存 array_layers、die_stack_depth 和各类 die_count，不能共用一个 layers 字段。

### 3.3 封装与热模型的最小参数

每片裸片记录工艺、长宽、位置、朝向、层级、功率域、时钟域和热节点。每个连接记录端口、物理类型、协议、位宽或 Lane 数、速率、方向、延迟、有效载荷比例、每 bit 能量和并发限制。共享 ADC、控制器或垂直通道只实例化一次。

TSV 是 Through-Silicon Via；Micro-bump 是微凸点；Hybrid Bonding 是混合键合。UCIe 是可选的 Die-to-Die 接口标准，具体版本和模式通过配置引用；其官方资料包含 3D 集成支持 [3]。连接到 UCIe 不自动意味着整个封装具备缓存一致性。

首版热模型提供 off、budget、rc 三种精度：off 仅报告功耗，不推断温度；budget 检查功率或外部给定温度是否越界，不计算温度场；rc 使用有来源的热阻热容及耦合关系估算温度。启用降频时，温度影响的服务率要反馈到执行时间线。没有校准数据时报告敏感性，不声称已完成封装热验证。

## 4 HBM 与 HBF 的存储层次

HBM 是 High Bandwidth Memory，通常采用堆叠 DRAM；HBF 是 High Bandwidth Flash，采用 Flash / NAND 存储技术。两者的容量、带宽、时延、访问粒度和写入行为分别建模。HBF 可以是系统数据供应层，不应因为具有较高带宽就直接复用 HBM 的访存语义。

| 参数范围 | HBM / DRAM | HBF / Flash |
| --- | --- | --- |
| 组织 | Stack、Channel、Pseudo-channel、Bank、Row | Die、Plane、Page、Block 和控制器并行性 |
| 服务行为 | 读写时序、行状态、读写切换、刷新 | 读取、编程、擦除、管理开销及读写不对称 |
| 粒度与路径 | 控制器可见的请求与突发粒度 | 原始介质粒度和接口可见粒度分别记录 |
| 约束 | 时序、容量、带宽和功率 | 还需考虑写入寿命、写放大及管理策略 |
| 数据策略 | 热数据、激活、工作区等 | 大容量权重与其他数据的放置、预取、缓存 |

Page、Program、Erase 等描述的是 Flash 介质行为；若具体 HBF 控制器隐藏这些操作，外部模型按接口公开的服务行为建模，内部模型按所选精度细化。不要未经核实就套用某个 SSD 的 FTL、队列或接口协议。

截至本规划所依据的公开资料，SK hynix 于 2026 年 8 月公布的 HBF 信息将其定位为 HBM 与 SSD 之间的存储层，并描述了 UCIe 连接及规格分档 [4]。建模应引用具体规格版本和实现数据；公告中的上限不等于某个访问模式下的持续性能。

### 4.1 HBF 与 CIM 的关系

HBF 作为供数存储，与使用 Flash 器件计算的 CIM，是两个独立能力。某个 HBF 产品不因采用 NAND 就自动具备 CIM 操作。若研究 HBF 与 3D CIM 的一体化方案，需要额外定义计算能力、访问冲突、外围、控制和误差模型。

一种候选数据路径是 HBF → 传输引擎 → HBM / SRAM 暂存 → CIM 权重装载；允许直接供数的设计另行声明路径。权重首次装载、换入换出、缓存命中、双缓冲和计算重叠都进入执行计划。是否值得增加 HBF，取决于容量需求、复用率和搬运开销。

训练与推理、Prefill 与 Decode、固定权重与动态张量分别评估。3D CIM 的权重容量增加后，仍需检查激活、KV Cache、部分和、转换器和网络是否成为新的瓶颈。

## 5 节点和集群设计

### 5.1 systemmodel 负责单节点

Node 组合 CPU Socket、主存、加速设备、板卡互连和 NIC。至少表达 NUMA 距离、PCIe Root Complex / Switch、Peer-to-Peer 可达性、DMA 引擎、设备本地内存和主机暂存路径。数据从 CPU 内存到 GPU、NPU 或 CIM，可能争用同一个 PCIe 上行口。

NIC 是 Network Interface Controller；NUMA 是 Non-Uniform Memory Access。RDMA 表示 Remote Direct Memory Access，但可否直达某个设备缓冲区仍取决于路径、地址注册和平台支持。CXL 相关协议能力分别配置，不能由存在 PCIe 物理连接推断其具有 CXL 一致性或内存扩展能力 [5]。

### 5.2 clustermodel 负责跨节点连接

| 对象 | 关键参数 | 需要解释的结果 |
| --- | --- | --- |
| Node 类型与数量 | 各类型设备、内存、NIC 和能力 | 异构容量、计算与通信不均衡 |
| NIC / Endpoint | 端口、带宽、队列、注入上限、卸载能力 | 发送接收瓶颈及主机开销 |
| Fabric / Switch | 拓扑、端口数、交换容量、缓冲、路由 | 共享路径、拥塞及双向流量 |
| Link | 速率、传播与协议延迟、有效负载、错误模型 | 实际传输时间与链路占用 |
| Rack / Pod 分组 | 成员、网络层次、电源和故障域 | 跨组通信与共享预算 |

Scale-up 表示紧耦合扩展域，Scale-out 表示更大范围的网络扩展；二者与“节点内”和“节点间”并非永久一一对应。机架级互连也可能形成 Scale-up 域。它们应作为 Fabric 的角色与能力，物理位置独立保存。

共享带宽、Oversubscription（超额订阅）、Bisection Bandwidth（二分带宽）、多 Rail 和路径选择影响扩展效率。不能把某条网络端口带宽乘以节点数，直接作为全部通信都能使用的带宽。

### 5.3 模型规模与精度

首版以消息、分块和流为网络仿真粒度，保留实际共享资源与争用。单个瓶颈链路需要时再细化为包或 Flit。节点内部可以采用经过校准的粗粒度 GPU 模型，同时对 3D CIM 保留更细的资源行为。

组件的细粒度和摘要模型必须具有相同的端口、操作语义和统计边界。一个组件不能同时运行详细模型并再额外收取一份摘要延迟。结果按资源声明精度，不能因为局部逐周期就声称全系统逐周期精确。

## 6 分布式映射与通信

### 6.1 硬件层次与并行策略分别选择

| 并行策略 | 英文术语 | 主要成本 |
| --- | --- | --- |
| 数据并行 | Data Parallelism，DP | 复制状态；训练时通常有梯度同步 |
| 张量并行 | Tensor Parallelism，TP | 算子内切分与频繁集合通信 |
| 流水并行 | Pipeline Parallelism，PP | 阶段传输、气泡、微批量及负载不均 |
| 专家并行 | Expert Parallelism，EP | MoE 路由、AllToAll、专家热点与权重驻留 |
| 上下文或序列并行 | Context / Sequence Parallelism | 序列切分、注意力交换与归约；具体策略单独定义 |

异构映射同时考虑支持操作、精度、形状效率、本地容量及通信代价。例如 CPU 处理控制与不规则任务，GPU 处理动态或高精度运算，NPU 处理匹配其数据流的张量任务，CIM 或 3D CIM 处理适合其编码和驻留方式的子图。这是候选分工，最终通过总成本比较决定。

Rank 是通信参与者标识；Rank 到进程、设备和资源的映射显式记录。不要固定一个 Rank 等于一张卡、一个裸片或一个核。不同资源速度不同时，分片比例可以不等，但必须满足算子语义和通信协议。

### 6.2 通信操作与执行过程

支持点对点 Send / Receive，以及 Broadcast、AllReduce、ReduceScatter、AllGather、AllToAll 等集合操作。操作记录通信组、成员次序、数据类型、元素数量或分段、归约运算、源目标缓冲及依赖。具体计数约束按操作种类校验 [6]。

集合操作由通信层选择 Ring、Tree、分层或其他算法，再展开为传输和局部归约。先节点内、后节点间的分层方案只是候选；拓扑、消息大小、设备能力和拥塞决定其实际表现。

跨设备搬运可能包含源内存读取、DMA、板级链路、NIC、网络、目标链路和内存写入。各阶段共享的资源都要计入，但相同物理传输只收费一次。Send 提交、源缓冲可复用、接收数据可见和集合完成分别定义，不能用一个未经说明的 done 替代。

一个均匀环上的简化 AllReduce 模型为 T ≈ 2(p−1)α + 2(p−1)N/(pB)。其中 p 是参与者数，N 是每个参与者的输入字节数，α 是每步延迟，B 是对应有效单向带宽。该式用于无其他争用、均匀分片的初筛，局部归约、协议、拓扑拥塞及计算重叠需另外建模。

集合算法可能改变浮点加法次序，CIM 输出还可能涉及量化与误差。端到端功能验证采用预先规定的精度和容差，不能仅因通信完成就认为数值正确。

## 7 配置和公共数据契约

### 7.1 类型模板与实际实例

配置区分组件类型、实际实例、连接、逻辑视图与工作负载放置。node_count、card_count、die_count 等数量用于展开实例；展开后由实体图计算派生数量，避免同时维护相互矛盾的总数和明细。

支持同构模板复用与按实例覆盖。例如集群可有 GPU 节点和 CIM 节点两种类型，也可以在一个节点中混合 GPU 卡和 CIM 卡。型号、介质、精度及封装模板不绑定数量固定的全局字段。

配置目录为 config/hardware/components、chips、systems、clusters，以及独立 config/costs。它们是按职责组织的配置文件目录；组件模板与实例引用关系才决定实际架构。

配置按默认值、类型模板、平台变体和实验覆盖解析，保存完整快照及哈希。改变底层结构后，重新校验所有使用该模板的实例、成本模型和执行计划。单实例覆盖需要明确目标 ID，不能悄悄改变全部同类型设备。

### 7.2 核心契约

| 契约 | 必备内容 | 使用边界 |
| --- | --- | --- |
| HardwareSpec | 资源实例、包含关系、端口、链路、域和 DeviceView | 延续现有名称，范围可扩展到整个实验平台 |
| ComponentSpec | 类型、能力、参数、模型和成本引用 | 支持芯片、节点和网络的分层组合 |
| MemoryRegion / TensorRef | 存储所有者、地址范围、形状、布局、精度与版本 | 明确数据当前位置及可访问性 |
| PlacementPlan | 子图、Rank、阶段与设备映射 | 编译映射与运行时共同遵守 |
| CommunicationPlan | 通信组、算法、分块、路径约束和依赖 | 与计算计划组合执行 |
| ExecutionPlan | 计算、存储、传输、同步及硬件快照哈希 | 可分层组织，但保持统一依赖语义 |
| SimulationResult / TraceEvent | 指标、资源范围、精度、版本和因果事件 | 支持芯片到集群逐层归因 |

Chip、System、Cluster 采用类型化的组合描述，统一解析到 HardwareSpec；避免另外维护三份互不一致的硬件真相。新增版本保留单芯片入口，单芯片任务无需先构造多机集群。

TensorRef 至少标明所有者和地址空间。软件统一地址不等于物理本地；统一内存迁移和页面错误需要所选模型明确支持。不能通过共享 Python 对象绕过本应发生的设备或网络传输。

### 7.3 跨模块调用边界

编译器读取能力和拓扑，不访问组件内部队列。组件通过端口请求接收、接受或拒绝、背压和完成通知交互。仿真器负责统一时间推进，运行时策略根据已经发生的事件决策。全局规划器不得读取仿真未来信息来消除真实等待。

组装器通过公共契约和模型工厂组合下层实例。chipmodel 不依赖 systemmodel、clustermodel 或编译器内部表示；底层组件也不需要知道自己属于几卡几机的实验。上层通过能力查询、端口和事件完成组合，禁止直接修改下层私有状态。

先采用单进程、公共整数时间单位的事件引擎。周期按各自时钟域转换；跨域适配及取整规则固定。后续若采用联合仿真，须定义时间前进边界和因果约束，不让各子模拟器独立计时后直接相加。

校验分为字段、结构与引用、端口及协议、地址与一致性、成本适用范围、工作负载映射六层。资源引用错误、不支持的精度、端口不兼容或缺少权重装载路径都应报告到具体实例与计划操作。合法拓扑中的网络超额订阅通过排队与拥塞体现，不直接当作配置错误。

## 8 可视化和参数扫描

界面采用同一配置源的多个视图：资源树查看 Cluster 到 Array；拓扑视图查看连接和共享链路；封装视图查看裸片平面位置与堆叠；映射视图查看子图和 Rank；时间线查看计算、搬运、归约与等待。图形坐标可以用于阅读，只有明确标记为物理坐标时才参与线长和成本计算。

选择资源后展示中英文名、单位、当前值、模板来源、单实例覆盖、依赖及成本依据。静态设计参数可编辑，运行中的状态和派生量只读；修改不能污染已开始运行的配置快照。

| 扫描层次 | 设计变量示例 | 同时观察的结果 |
| --- | --- | --- |
| CIM / 3D CIM | 阵列层数、激活层数、ADC 共享、权重位宽 | 容量、吞吐、误差、外围占用 |
| Package | 计算裸片数、堆叠顺序、垂直带宽、功率预算 | 跨裸片流量、温度或约束违例、降频 |
| 存储层次 | HBM / HBF 容量、缓存、预取及装载策略 | 权重驻留、停顿、写入和迁移成本 |
| Node | GPU / NPU / CIM 数量、PCIe 拓扑、NIC 绑定 | 本地争用、NUMA 访问和设备利用率 |
| Cluster | 节点类型比例、链路与交换层次 | 通信时间、拥塞、扩展效率、能耗 |
| 软件映射 | DP / TP / PP / EP、分片、微批量、算法 | 完成时间、内存峰值、通信量和精度 |

改变硬件后重新映射与保留映射的敏感性实验分别标注。后一种仍要验证合法性并导出绑定新硬件哈希的计划。参数组合可能不可实现，搜索空间需要联动约束，而非无条件笛卡尔积。

## 9 实施顺序与验收

先固定接口和最小可执行路径，再扩大物理范围。下表 S1–S7 是异构扩展的工作分解；总体实现门槛使用 docs/architecture/validation.md 中的 A–F，两者分别编号。各层支持摘要模型，单卡系统实验与详细 CIM 研究可共享接口并独立推进。

| 阶段 | 实现范围 | 完成条件 |
| --- | --- | --- |
| S1 | 参数字典、实例图、端口、能力与成本接口 | 单芯片配置有效，模板展开及引用唯一 |
| S2 | 数字基线和 CIM 单芯片、多核与共享存储 | 功能正确；端口争用与流水线可手算 |
| S3 | Dual-Die、局部 3D 堆叠、3D CIM 和 HBF 模型 | 跨层与装载路径明确；热及介质简化条件可追踪 |
| S4 | 单节点 CPU 加多类设备、多卡互连 | 共享 PCIe / 内存瓶颈可重现，数据可见性正确 |
| S5 | 两节点、NIC、交换网络和点对点传输 | 网络竞争与完成时间符合基准案例 |
| S6 | 集合通信与混合并行映射 | Rank、操作序列、功能结果与时间线一致 |
| S7 | 规模探索与关键成本校准 | 多方案比较可复现，模型误差与敏感性可解释 |

S3 的 3D CIM 电路细化和 S4 的节点组合可以在接口固定后分别推进，不要求先具备完整晶体管级模型。首个集群闭环采用 2 节点，每节点控制 CPU 加 2 个加速设备，以小规模点对点和 AllReduce 验证通信。设备类型可从两个相同设备逐步替换为 GPU 与 CIM；生产规模数量通过配置扩展。

### 9.1 最小验证集合

- 结构验证：两裸片合成一个逻辑设备不重复计数；一个节点可混用不同卡；可选层次省略后引用仍有效。
- 功能验证：CIM 编码、跨层归约、数据迁移和集合操作与独立参考一致；明确混合精度容差。
- 资源验证：共享 ADC、垂直链路、HBM 控制器、PCIe 上行和 NIC 产生可解释的等待。
- 边界验证：无可达路径、容量不足、不支持操作、非法 Rank 组及未知成本不会生成正常性能结论。
- 扩展验证：带宽趋小会暴露等待；带宽增大后可能转为计算受限。精度或映射变化时不强求性能单调。
- 校准验证：摘要模型在其声明的输入和争用范围内对齐细模型或实测；范围外明确失效。

### 9.2 指标与实验口径

同时报告任务延迟、吞吐、能量、存储峰值、通信字节、等待原因和每层利用率。训练可报告 Step Time，推理可报告 TTFT、TPOT 及吞吐；这些指标的起止点、批量、并发和预热条件必须固定。

Strong Scaling 固定总工作量，Weak Scaling 随资源增加工作量。异构规模比较报告具体资源清单、面积或功率预算；只有明确同类基线和理想加速比例时，才使用对应的并行效率公式。

芯片功耗、板卡功耗、节点功耗和设施功耗分别划界。共享交换机不能按每个通信参与者重复计入整机功耗；采用 PUE 时注明 IT 功耗边界，避免将已包含的冷却成本再乘一次。

## 10 目录与实现位置

以下目录已建立，作为后续执行模型的实现位置；原有 chipmodel/compute、memory、interconnect、control 保留。目录是代码职责划分，实际资源组成由配置决定。

```text
chipmodel/
  compute/          CPU GPU NPU CIM 与 3D CIM 执行模型
  memory/           SRAM DRAM Flash 与控制器
  interconnect/     片内及 Die-to-Die 连接
  control/          芯片发射 仲裁 同步
  composition/      Tile Die Package 组合
  packaging/        裸片位置 堆叠 物理连接 热参数
systemmodel/
  composition/      Board Card Node
  io/               PCIe CXL DMA NIC 与地址路径
clustermodel/
  composition/      Cluster 与资源分组
  fabric/           交换机 跨节点链路 路由与争用
runtime/
  dispatch/         软件队列 派发与动态策略
  communication/    集合通信算法与分块
contracts/          公共类型与格式
configuration/      参数字典 解析 校验与冻结
costmodel/          条件成本 特征化与不确定性
artifacts/          清单 序列化 存储与来源
ui/                 参数表单 拓扑 映射与时序视图
```

NIC 的硬件状态由实例所属的 systemmodel 维护，clustermodel 引用其端口；需要细化 NIC 内部时再组合 chipmodel 资源。同一个物理组件只有一份状态。公共端口和事件定义放在 contracts，具体时序适配仍由对应模型负责。

现有 compiler/src/globalsplit、globalsolver、tiling、memplan、sched、lowering 和 export 按阶段扩展跨设备支持，不立即复制一套集群编译器。现有 simulator 和 evaluation 继续承担统一执行、实验管理与结果分析。主模块的 README.md 与 docs/design.md 说明子目录、状态、输入输出和验证责任；本次建立结构，不代表已完成执行实现。
