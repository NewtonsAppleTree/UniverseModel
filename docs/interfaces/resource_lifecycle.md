# 请求与数据的生命周期

## 1 范围与最重要的不变量

本文件细化[公共契约](contracts.md)，用于未来实现接口，不表示已有状态机。一次操作的提交、硬件接收、读取源数据、释放源缓冲、目标可见和全局同步可以发生在不同时间。只有明确这些时刻，异步搬运、双缓冲、CIM 权重更新和多机通信才可正确组合。

必须同时守住：数据版本不提前可见；仍被使用的区域不被复用；请求不重复产生效果；失败或取消后的资源与数据状态可解释。宿主数组的生命周期不能代替目标内存的生命周期。

## 2 身份不能只使用一个 operation_id

| 身份 | 回答的问题 | 使用边界 |
| --- | --- | --- |
| run_id / run_epoch | 属于哪次运行或复位世代 | 拒绝上一轮残留事件 |
| operation_id | 属于计划中的哪次逻辑工作 | 性能归因与依赖 |
| request_id / attempt_id | 哪个请求及哪次提交尝试 | 背压重试、重复确认和去重 |
| allocation_id / generation | 哪一代实际分配 | 地址复用后拒绝旧引用 |
| data_id / content_version | 哪个逻辑数据及内容版本 | 副本、原地更新和一致性 |
| chunk_id / region | 哪一部分可使用 | 分块流水和部分写入 |

地址相同不等于分配相同，逻辑数据相同不等于副本同样有效。可以通过全局唯一分配 ID 实现世代隔离，也可显式维护 generation；公共效果必须等价。

同一 request_id 的重复提交若已被接收，应返回已有接收/结果状态或明确拒绝，不再次执行。未接收的重试不能提前修改目标内容。attempt_id 用于诊断，不赋予重复请求新的逻辑工作身份。

## 3 接收与资源承诺

提交接口明确返回 accepted、retryable_backpressure 或 rejected。accepted 表示组件承担请求的后续完成/失败责任；它承诺哪些队列槽、源数据保护或目标空间，需要由端口协议声明。不能只返回 accepted，却把请求留在双方都不管理的位置。

软件队列满、硬件队列满、源数据未就绪、目标空间不足和带宽竞争是不同等待原因。接收队列槽不等于已经取得执行槽；接受请求也不等于已复制源数据。若接收时就复制到内部缓冲，应显式计入缓冲容量、搬运和访问成本。

背压不改变逻辑数据。等待策略应选择完成通知、credit 返回或规定的轮询间隔；零时间连续重试既会制造不合理吞吐，也可能使仿真引擎无法前进。

## 4 数据相关的完成里程碑

| 里程碑 | 可推导的事实 | 仍不能推导的事实 |
| --- | --- | --- |
| accepted | 某组件已承担请求 | 源缓冲可覆盖 |
| source_consumed | 请求不会再读取该源版本/区域 | 远端已经看见数据 |
| delivered | 数据抵达协议定义的接收边界 | 目标计算单元已可读 |
| destination_visible | 指定目标域可读取完整版本或 chunk | 其他一致性域也可读 |
| durable | 数据在指定故障模型下已持久化 | 所有设备已完成同步 |
| operation_completed | 该操作声明的全部效果满足 | 所有相关操作或整个通信组完成 |

不是所有操作都需要全部事件，首次实现可以合并里程碑，但必须声明合并后的强语义。例如完整 memcpy 的 completed 可定义为源已消费且目标已可见；不能只定义为排队成功。Flash/HBF 只有在研究持久性或恢复时才需要 durable，读写完成与介质持久化依具体接口分别规定。

发送端本地完成和接收端数据可见分别表达。集合通信 completed 需要达到其组内协议定义的完成条件；不能由任一 P2P send 的确认替代。

## 5 缓冲区与版本的所有权

建议把分配的存在、内容的有效性和访问占用分开记录。分配可以处于 allocated/releasing/freed；内容可以是 uninitialized、producing、valid、invalid；访问占用则是读者/写者或受保护区域的集合。单一 busy 标志不足以表达多个读者与分块写入。

编译器生成静态生命周期和别名依据；实际运行中的延期释放、异步读取与动态 buffer 由 runtime/拥有内存的组件按协议管理。所有者唯一，其他模块只持租约或引用，不各自维护一份可独立改变的有效性。

原地更新须显式描述允许的读写顺序。完整张量版本只有全部规定区域有效后才发布；流式消费可以先发布 chunk 版本，但必须有明确范围和依赖。部分失败时不能把尚未完成的整张量标为 valid。

## 6 取消与复位不是撤销物理历史

cancel_requested 是控制请求，不是终态。未开始操作可在撤销队列项并释放承诺资源后取消；已开始操作按模型能力选择拒绝取消、在安全边界停止，或执行到排空后终止。不能通过删除一个未来完成事件，就认定资源和数据已恢复初态。

取消前已经发生的读取、网络流量、能耗和部分写入保留。终态 cancelled 需保证不会再产生未说明的后续效果；被保留的部分输出、失效区域与资源释放均写入诊断。某操作可以正常完成，而所属用户请求已取消并不再消费结果，这两个状态需要分开。

复位建立新 epoch，按组件协议重置队列/状态，并使旧事件失效；旧事件失效不等于硬件故障恢复已经建模。若模拟真实复位，要计入目标时间、数据丢失范围与恢复工作；若仅重置模拟器以开始新实验，不把宿主初始化时间计入目标设备时间。

## 7 时间顺序与仲裁

统一事件排序可采用 `(target_time, delta_round, phase, sequence)`。同一轮先完成/释放，再更新可见性与依赖，再策略回调与仲裁；若新事件需要返回更早的 phase，则进入下一 delta_round。不得在同一轮向已经处理过的阶段插入事件。

delta_round 只用于同一目标时刻的因果闭包，不表示额外硬件周期。无限零时间级联应报告模型无进展；固定排序也不等于公平仲裁。资源应声明 FIFO、round-robin、优先级、年龄等策略，并验证饥饿行为；不能依靠实例 ID 排序“顺便”决定所有硬件竞争结果。

多个资源的获取要有统一规则：原子取得、固定获取顺序，或显式允许部分持有并建模死锁。credit 返回、目标缓冲释放、源端口释放使用各自时刻，避免永久锁住链路或提前重用空间。

## 8 死锁与暂时无事件

待处理工作无未来事件时，先判断是否有合法外部到达、定时器或必须重新触发的仲裁。若没有，应输出等待图：操作等待哪个资源/数据版本，资源由谁持有，哪个通知缺失。不能仅增加仿真超时掩盖死锁。

容量不可满足、参与者永远缺失、协议死锁、策略饥饿和输入流已经结束分别诊断。持续有事件但有效工作长期不前进是 livelock/starvation 问题，不能仅靠“事件队列非空”判定运行正常。

## 9 最小验证证据

首版至少覆盖：接收后延迟读取；发送源释放早于目标可见；两个读者共享源缓冲；相同地址重新分配；背压后重试；开始前取消；开始后拒绝取消/安全排空；旧 epoch 的延迟事件；同时间释放与发射。

每个案例保存初态、事件顺序、数据版本与资源租约。可手算案例见[设计取舍示例](../methods/design_tradeoff_examples.md)。这些案例是未来语义验证目标，当前没有可执行状态机。
