# runtime：执行策略与软件开销

## 核心与状态

最重要的是策略只能依据已经发生的信息提交合法工作。runtime 依赖 contracts，拥有软件就绪队列、streams、通信进度和策略状态；不维护硬件队列副本，不直接推进全局时间。

`dispatch` 管派发，`streams` 管顺序与同步，`communication/p2p` 管点对点，`collectives` 展开集合通信，`policies` 管动态选择。runtime 模拟目标系统软件行为；宿主程序运行 runtime 本身的耗时另计。

## 输入输出与参数

输入是执行/放置/通信计划、只读能力、完成/背压通知与到达请求。输出为组件请求、同步操作、追加计划记录和策略观测。关键参数包括 launch overhead、软件队列深度、in-flight limit、stream 数、batch policy、优先级、chunk size 和 collective 算法。

目标 CPU 上的调度开销可以作为模拟延迟或显式 CPU 工作，二者择一计费；不能既忽略 CPU 占用又假定无限并发调度。策略决策若依赖状态快照，应声明可观测延迟，不能读未来信息。

## 工作链与通信

接收任务 → 判断依赖与数据可见 → 选择合法目标/路径 → 请求提交 → 接收或等待背压 → 完成更新 → 解锁后继。重试保持请求身份，避免重复执行；failed/cancelled 需传播到依赖者并形成终止原因。

collective 先核对 group/sequence/dtype/reduction，再选择 ring/tree/分层算法，展开为 P2P 与局部规约。网络与节点资源实际决定完成时间。集合通信语义、分片规则和算法选择分别保存。

## 参数逻辑与优化

增加 in-flight 可隐藏等待，但增加队列、buffer 活跃量和排队延迟；通过 M07/M09 检查稳定性与容量。增大通信 chunk 可降低启动开销，也可能减少重叠并造成尾部等待；M13 仅提供理想算法基线。

推理服务关注到达率、批处理和尾延迟；离线吞吐关注流水重叠；异构执行关注迁移/格式转换；多机任务关注 straggler 与通信顺序。离线 oracle 可以作为上界对照，但必须标为不可实现的先知基准。

## 验证与保存

验证 stream 顺序、背压、取消、重试、缺失参与者和无未来信息。相同输入与策略版本应能复现；随机策略独立记录种子。保存动态决策、队列等待原因、追加操作及调度成本口径。

## 异步操作与服务负载补充

cancel_requested、源缓冲释放、目标可见及用户请求的终态分别维护；在途工作按能力拒绝取消或安全排空，不能假定撤销历史效果，见[生命周期规范](../../docs/interfaces/resource_lifecycle.md)。动态 batching/admission 需要保存实际到达与接纳时刻，未完成请求参与统计，见[实验有效性](../../docs/methods/experiment_validity.md)。
